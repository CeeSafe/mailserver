# mauth

Inbound mail authentication: SPF (RFC 7208), DKIM (RFC 6376, with RFC 8301's algorithm rules and RFC 8463's
Ed25519) and DMARC (RFC 7489), and the Authentication-Results field (RFC 8601) that records them. msmtp runs it on
port 25 only.

```ceesafe
var dkim = DkimVerifier.create();
dkim.feed(chunk)?;                                     // as DATA arrives
var report = AuthReport.create();
await authenticate(resolver, clientIp, mailFrom, helo, mut dkim, unixNow, mut report)?;
authenticationResults("mx.example.org", report, mut header)?;
match (report.dmarc.disposition) { DmarcPolicy.Reject => … , DmarcPolicy.Quarantine => … , _ => … }
```

## SPF

- **Coverage:** every mechanism and modifier, and every macro with its transformers and URL escaping. `exp=`
  explanations are fetched for a Fail.
- **The RFC's limits:**
  - 10 DNS-querying terms;
  - 2 void lookups;
  - 10 names per `mx` and `ptr`.
- **Syntax:** the whole record is parsed before anything is evaluated, so a syntax error anywhere is a PermError.
- **Checked against the SPF council's suite.** `tests/spf/run.py` runs `rfc7208-tests.yml` (from pyspf): 203 tests
  in 16 scenarios, each zone served by mdns's fakedns. 203 pass. One allowed deviation is the case of hex digits in
  one explanation text, which DNS ignores.

## DKIM

- **Streaming.** The verifier is fed DATA as it arrives. It keeps the header block (up to 1 MiB), and from the blank
  line on it hashes the body for each signature, in its canonicalization and with any `l=` limit. Nothing is read
  twice.
- **What it checks:**
  - simple and relaxed canonicalization, for header and body;
  - repeated headers picked from the bottom up;
  - the signature's own `b=` removed before hashing;
  - `rsa-sha256`, with keys under 1024 bits refused (RFC 8301), and `ed25519-sha256`;
  - `x=` expiry;
  - that `i=` lies within `d=` and that From is signed;
  - revoked keys (`p=`);
  - at most 5 signatures per message.
- **Signatures** are checked through OpenSSL, in `CeeSafeLibs/pkey`.
- **Checked against dkimpy.** `tests/dkim/run.py` runs 78 cases (`tests/dkim/gen.py`). 72 were signed by dkimpy:
  - 8 bodies × 4 canonicalizations × RSA and Ed25519;
  - over-signing, `l=`, a 1024-bit key, two signatures;
  - tampering of the body and headers, a revoked key.

  Four more are MimeKit's real Gmail-signed messages and RFC 8463's example. All 78 give dkimpy's verdict.

## DMARC

- **Policy lookup:** the record at `_dmarc.<From domain>`, else at its organizational domain (with `sp=`).
- **Tags:** `p`, `sp`, `adkim`, `aspf` and `pct`.
- **What makes a pass:** an aligned SPF pass or DKIM pass, relaxed or strict.
- **What is refused:**
  - several From fields or From domains give PermError;
  - several records, or a malformed one, mean no policy;
  - a DNS failure gives TempError, never a rejection.
- **Organizational domains** come from the full Public Suffix List, both ICANN and private sections, as OpenDMARC
  uses it. `src/psl.cee` is generated by `tools/psl.py` (10,406 rules, IDNs as A-labels). The C# server used a
  hand-picked list of 70 suffixes, which its own comment called a stopgap.

## In msmtp

- **The header:** every message accepted on port 25 starts with `Authentication-Results: <hostname>; spf=…;
  dkim=…; dmarc=…`. Any field in the message claiming our hostname is removed (RFC 8601 §5), since a sender could
  forge one to look verified.
- **DMARC dispositions:**
  - `reject` refuses the message at the end of DATA (550 5.7.1);
  - `quarantine` delivers it to the recipient's Junk folder.

## Tests

- `tests/run.sh`: unit tests, and an end-to-end `authenticate` against fakedns.
- `tests/spf/run.py` and `tests/dkim/run.py`: the two differentials.

## Signing

`DkimSigner` (`src/sign.cee`) signs outgoing mail for the relay (mqueue):

```ceesafe
var signer = DkimSigner.create();
signer.feed(piece)?;  …                                // the message, in pieces
signer.fromDomain(mut domain)?;                        // whose key to use
signer.sign(key, "example.org", "s1", now, mut field)?;  // "DKIM-Signature: …\r\n", to send first
```

- It uses relaxed/relaxed canonicalization, with RSA-SHA256 or Ed25519-SHA256 (RFC 8463). Keys come from
  `pkey.PrivateKey`.
- The header is kept and the body only hashed, by the same canonicalization code as the verifier.
- It signs the fields that matter for display, threading and lists. From, To, Cc, Subject, Date and Reply-To are
  oversigned, so none can be added after signing.
- **Tested:** `tests/dkim/sign.py` signs the 78 verifier cases plus 7 edge cases with an RSA key and an Ed25519 key
  made by openssl: 170 signed messages, each verified by dkimpy and by our own verifier. The edge cases are trailing
  spaces, an empty body, no final CRLF, folding, repeated fields, UTF-8 and a lone CR.
